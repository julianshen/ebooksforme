第 4 章：SCALE 層

第 4 章：SCALE 層 — 讓 Agent 可靠運行

4.1 問題：Agent 在生產環境會遇到什麼？

開發環境和生產環境是兩個完全不同的世界。

在開發環境，Agent 跑在你的筆記本電腦上，網路穩定，資源充足，你可以隨時查看日誌。在生產環境，Agent 跑在 Kubernetes 集群中，面臨：

  • 節點故障：物理機器或 VM 突然當機
  • 網路分區：Agent 與 Orchestrator 之間的網路中斷
  • 資源耗盡：記憶體洩漏導致 OOMKilled
  • 依賴故障：LLM API 逾時或返回錯誤
  • 狀態丟失：Pod 重啟後所有上下文消失

SCALE 層的目標是讓 Agent 在這些情況下依然可靠運行。

4.2 Google AX 深度解析：Durable Execution

Google AX（Agent Executor）是 Google 開源的分散式 Agent Runtime，專門解決 Agent 在生產環境的可靠性問題。本章從原始碼層面深入剖析其設計與實作。

4.2.1 AX 是什麼？

AX 是一個分散式 Agent Runtime，提供以下核心能力：

  • Durable Execution：Agent 執行狀態持久化到資料庫，故障後可恢復
  • Multi-Agent Orchestration：支援多個 Agent 協作，Agent 之間通過 gRPC 通訊
  • Event Sourcing：所有操作以事件形式記錄，支援重放和審計
  • Code Execution：內建安全的程式碼執行環境（gVisor + K8s）
  • Human-in-the-Loop：支援需要人工確認的任務

4.2.2 AX 架構總覽

AX 採用控制面/資料面分離的架構：

組件職責原始碼位置

Executor執行 Agent 的實際運算邏輯internal/controller/executor/

4.2.3 AX Protobuf 協議設計

AX 使用 gRPC 作為通訊協議，核心定義在 proto/ax.proto：

// AgentService 是 AX 的核心服務
service AgentService {
  // 雙向串流：Agent 與 Controller 之間的長連接
  rpc Connect(stream Message) returns (stream Message);
}

message Message {
  string message_id = 1;
  string invocation_id = 2;  // 一次完整的 Agent 執行
  string author = 3;         // 訊息來源（user/agent/tool）
  repeated Content content = 4;
  Metadata metadata = 5;
}

message Content {
  oneof kind {
    Text text = 1;
    FunctionCall function_call = 2;
    FunctionResponse function_response = 3;
    ConfirmationRequest confirmation_request = 4;
    ConfirmationResponse confirmation_response = 5;
    Error error = 6;
  }
}

設計亮點：

  • invocation_id 標記一次完整的執行流程，所有相關事件共享同一 ID
  • author 區分 user、agent、tool，便於審計和除錯
  • Content 使用 oneof，支援多種內容類型同時保持類型安全
  • ConfirmationRequest/Response 實現 Human-in-the-Loop

4.2.4 Controller：請求入口與狀態管理

Controller 是 AX 的入口點，負責：

  1. 接收用戶請求並建立新的 Invocation
  2. 找到對應的 Executor 執行 Agent
  3. 將事件寫入 EventLog
  4. 處理 Agent 返回的結果

Controller 核心流程（簡化）：

func (c *Controller) Invoke(ctx context.Context, req *InvokeRequest) (*InvokeResponse, error) {
    // 1. 生成 invocation_id
    invocationID := uuid.New().String()
    
    // 2. 初始化事件日誌
    eventLog, err := c.executor.NewEventLog(invocationID)
    if err != nil {
        return nil, err
    }
    
    // 3. 寫入用戶請求事件
    eventLog.Append(&Event{
        Type: EventTypeUserMessage,
        Author: "user",
        Content: req.Message,
    })
    
    // 4. 找到對應的 Agent 並執行
    agent := c.registry.Get(req.AgentID)
    result, err := c.executor.Execute(ctx, agent, eventLog)
    
    // 5. 返回最終結果
    return &InvokeResponse{
        InvocationID: invocationID,
        Result: result,
    }, nil
}

4.2.5 Executor：Durable Execution 的實現

Executor 是 AX 最關鍵的組件，負責實際執行 Agent 並確保狀態可恢復。

EventLog 的設計：

// internal/controller/executor/eventlog.go
type EventLog interface {
    // 追加事件（持久化）
    Append(event *Event) error
    
    // 讀取所有事件（用於恢復狀態）
    ReadAll() ([]*Event, error)
    
    // 獲取下一個事件索引
    NextIndex() int64
    
    // 關閉日誌
    Close() error
}

EventLog 是 Durable Execution 的基礎。每次 Agent 產生事件、呼叫工具、收到回應，都會被追加到 EventLog。如果 Executor 崩潰，新的 Executor 可以從 EventLog 恢復狀態並繼續執行。

SQLite 實現細節：

// internal/controller/executor/sqlite.go
type SQLiteEventLog struct {
    db *sql.DB
    invocationID string
}

func (l *SQLiteEventLog) Append(event *Event) error {
    data, err := proto.Marshal(event)
    if err != nil {
        return err
    }
    
    _, err = l.db.Exec(
        "INSERT INTO events (invocation_id, idx, data) VALUES (?, ?, ?)",
        l.invocationID, event.Index, data,
    )
    return err
}

func (l *SQLiteEventLog) ReadAll() ([]*Event, error) {
    rows, err := l.db.Query(
        "SELECT data FROM events WHERE invocation_id = ? ORDER BY idx",
        l.invocationID,
    )
    // ... 反序列化
}

SQLite 是預設後端，適合單機部署。生產環境可以替換為 PostgreSQL、Spanner 等分散式資料庫。

4.2.6 可恢復執行的實作機制

AX 的可恢復執行基於以下原則：

  1. 確定性重放：Agent 的邏輯必須是確定的，相同的輸入產生相同的輸出
  2. 外部呼叫快取：LLM 呼叫、工具呼叫的結果記錄在 EventLog，重放時直接返回
  3. 狀態快照：Agent 的內部狀態定期快照
  4. 檢查點：在關鍵節點建立檢查點，支援從檢查點恢復

恢復流程：

func (e *Executor) Resume(ctx context.Context, invocationID string) error {
    // 1. 載入事件日誌
    eventLog, err := e.LoadEventLog(invocationID)
    if err != nil {
        return err
    }
    
    // 2. 重建 Agent 狀態
    events, err := eventLog.ReadAll()
    if err != nil {
        return err
    }
    
    // 3. 重放到最後一個狀態
    state := e.replayEvents(events)
    
    // 4. 繼續執行
    return e.Continue(ctx, state, eventLog)
}

func (e *Executor) replayEvents(events []*Event) *AgentState {
    state := NewAgentState()
    for _, event := range events {
        switch event.Type {
        case EventTypeUserMessage:
            state.AddUserMessage(event.Content)
        case EventTypeModelResponse:
            // 重放時直接使用記錄的結果
            state.AddModelResponse(event.Content)
        case EventTypeToolResult:
            state.AddToolResult(event.Content)
        }
    }
    return state
}

4.2.7 Agent 執行流程詳解

AX 的 Agent 執行採用事件驅動模型：

func (e *Executor) Execute(ctx context.Context, agent Agent, eventLog EventLog) (*Result, error) {
    state := NewAgentState()
    
    for {
        // 1. Agent 處理當前狀態，產生下一步動作
        action, err := agent.Act(ctx, state)
        if err != nil {
            return nil, err
        }
        
        // 2. 記錄 Agent 產生的事件
        eventLog.Append(&Event{
            Type: EventTypeAgentAction,
            Content: action,
        })
        
        // 3. 根據動作類型處理
        switch action.Type {
        case ActionTypeRespond:
            // Agent 決定直接回應用戶
            return &Result{Response: action.Content}, nil
            
        case ActionTypeCallTool:
            // 執行工具
            result, err := e.executeTool(ctx, action.ToolCall)
            if err != nil {
                return nil, err
            }
            eventLog.Append(&Event{
                Type: EventTypeToolResult,
                Content: result,
            })
            state.AddToolResult(result)
            
        case ActionTypeRequestConfirmation:
            // 需要人工確認，暫停執行
            return &Result{
                Status: ResultStatusPaused,
                ConfirmationRequest: action.Confirmation,
            }, nil
        }
    }
}

4.2.8 AX 與 ADK 的橋接

AX 提供 Python ADK 適配器，讓 ADK Agent 可以作為 AX Agent 運行：

# python/adk/adk_agent_server.py 簡化版
class ADKAgentServicer(ax_pb2_grpc.AgentServiceServicer):
    async def Connect(self, request_iterator, context):
        async for request in request_iterator:
            invocation_id = request.invocation_id
            
            # 1. 為每次 invocation 創建獨立 session
            session_id = str(uuid.uuid4())
            session = await self.session_service.create_session(
                app_name=self.agent.name,
                user_id="AX_USER",
                session_id=session_id,
            )
            
            # 2. 水合歷史消息
            for msg in request.historical_messages:
                await self._append_message(session, msg)
            
            # 3. 執行最後一條消息
            async for event in self.runner.run_async(
                session_id=session.id,
                user_id=session.user_id,
                new_message=request.content,
            ):
                # 4. 將 ADK Event 轉換為 AX Message
                yield self._convert_event_to_message(event)
            
            # 5. 清理 session
            await self.session_service.delete_session(
                app_name=self.agent.name,
                user_id=session.user_id,
                session_id=session.id,
            )

轉換細節：

  • ADK 的 Event 對應 AX 的 Message
  • ADK 的 FunctionCall 對應 AX 的 FunctionCall
  • ADK 的 FunctionResponse 對應 AX 的 FunctionResponse
  • ADK 的 Text 對應 AX 的 Text

4.3 Agent Runtime

Agent Runtime 是 Agent 的執行環境。它需要處理：

4.3.1 生命週期管理

每個狀態轉換都需要持久化，確保故障後可恢復。

4.3.2 健康檢查

type HealthChecker struct {
    interval time.Duration
    timeout  time.Duration
}

func (h *HealthChecker) Check(agent *Agent) HealthStatus {
    // 1. 檢查程序是否存活
    if !agent.IsAlive() {
        return HealthStatusDead
    }

    // 2. 檢查心跳
    if time.Since(agent.LastHeartbeat) > h.timeout {
        return HealthStatusUnresponsive
    }

    // 3. 檢查資源使用
    if agent.MemoryUsage > 0.9 {
        return HealthStatusResourceExhausted
    }

    return HealthStatusHealthy
}

4.3.3 自動恢復

func (r *Runtime) HandleFailure(agent *Agent, status HealthStatus) {
    switch status {
    case HealthStatusDead:
        // 重新啟動 Agent
        r.RestartAgent(agent)

    case HealthStatusUnresponsive:
        // 先嘗試優雅重啟
        if err := r.GracefulRestart(agent); err != nil {
            // 失敗則強制重啟
            r.ForceRestart(agent)
        }

    case HealthStatusResourceExhausted:
        // 遷移到資源充足的節點
        r.MigrateAgent(agent)
    }
}

type SessionManager struct {
    hotStore  *redis.Client      // 活躍 Session
    warmStore jetstream.KeyValue  // 近期 Session
    coldStore *s3.Client          // 歷史 Session
}

func (sm *SessionManager) GetSession(ctx context.Context, id string) (*Session, error) {
    // 1. 嘗試從 Hot Store 讀取
    if session, err := sm.hotStore.Get(ctx, id); err == nil {
        return session, nil
    }

    // 2. 嘗試從 Warm Store 讀取
    if entry, err := sm.warmStore.Get(ctx, id); err == nil {
        session := deserialize(entry.Value())
        // 提升到 Hot Store
        sm.hotStore.Set(ctx, id, session)
        return session, nil
    }

    // 3. 從 Cold Store 讀取
    return sm.coldStore.Get(ctx, id)
}

func (sm *SessionManager) SaveSession(ctx context.Context, session *Session) error {
    // 儲存到 Hot Store
    if err := sm.hotStore.Set(ctx, session.ID, session); err != nil {
        return err
    }

    // 異步儲存到 Warm Store
    go func() {
        data, _ := json.Marshal(session)
        sm.warmStore.Put(ctx, session.ID, data)
    }()

    return nil
}

4.5 Memory Bank

Memory Bank 是 Agent 的長期記憶。與 Session 不同，它跨 Session 持久存在。

4.5.1 記憶類型

type MemoryType string

const (
    MemoryTypePreference  MemoryType = "preference"  // 使用者偏好
    MemoryTypeFact        MemoryType = "fact"        // 學到的事實
    MemoryTypeInteraction MemoryType = "interaction" // 互動摘要
    MemoryTypeContext     MemoryType = "context"     // 應跨 Session 的上下文
)

type Memory struct {
    ID        string     `json:"id"`
    UserID    string     `json:"user_id"`
    Type      MemoryType `json:"type"`
    Content   string     `json:"content"`
    Keywords  []string   `json:"keywords"`
    Importance float32   `json:"importance"` // 0-1
    CreatedAt time.Time  `json:"created_at"`
    UpdatedAt time.Time  `json:"updated_at"`
}

4.5.2 檢索機制

func (mb *MemoryBank) Retrieve(ctx context.Context, userID string, query string, limit int) ([]*Memory, error) {
    // 1. 關鍵字匹配（簡易）
    keywords := extractKeywords(query)

    // 2. 向量相似度（生產環境）
    queryEmbedding := mb.encoder.Encode(query)

    // 3. 組合檢索
    memories := mb.db.Query(ctx, userID, keywords, queryEmbedding, limit)

    // 4. 按重要性排序
    sort.Slice(memories, func(i, j int) bool {
        return memories[i].Importance > memories[j].Importance
    })

    return memories, nil
}

4.5.3 記憶壓縮

長期記憶會不斷增長。我們需要壓縮機制：

func (mb *MemoryBank) Compact(ctx context.Context, userID string) error {
    // 1. 獲取該使用者的所有記憶
    memories := mb.db.GetByUser(ctx, userID)

    // 2. 按時間分組
    groups := groupByTime(memories, time.Hour*24)

    // 3. 每組生成摘要
    for _, group := range groups {
        summary := mb.llm.Summarize(group)

        // 4. 儲存摘要，刪除原始記憶
        mb.db.Save(ctx, &Memory{
            UserID:   userID,
            Type:     MemoryTypeInteraction,
            Content:  summary,
            Importance: calculateImportance(group),
        })

        mb.db.DeleteBatch(ctx, group)
    }

    return nil
}

4.6 Sandbox 控制器

Sandbox 控制器負責動態建立和銷毀 Agent 的執行環境。

4.6.1 設計

type SandboxController struct {
    k8sClient kubernetes.Interface
    factory   *SandboxFactory
    scheduler *SandboxScheduler
}

func (sc *SandboxController) CreateSandbox(ctx context.Context, spec *SandboxSpec) (*Sandbox, error) {
    // 1. 選擇隔離等級
    isolation := sc.selectIsolation(spec.AgentType, spec.IsolationLevel)

    // 2. 選擇節點
    node := sc.scheduler.SelectNode(spec.Resources, isolation)

    // 3. 建立 Pod
    pod := sc.factory.CreatePod(spec, isolation, node)

    // 4. 等待就緒
    if err := sc.waitForReady(ctx, pod); err != nil {
        sc.cleanup(pod)
        return nil, err
    }

    return &Sandbox{Pod: pod}, nil
}

4.6.2 隔離等級選擇

func (sc *SandboxController) selectIsolation(agentType string, requested IsolationLevel) IsolationConfig {
    // 預設隔離策略
    defaults := map[string]IsolationConfig{
        "coding":   {Runtime: "runc", NetworkPolicy: "restricted"},
        "browser":  {Runtime: "gvisor", NetworkPolicy: "permissive"},
        "data":     {Runtime: "runc", NetworkPolicy: "restricted"},
        "review":   {Runtime: "runc", NetworkPolicy: "restricted"},
    }

    config := defaults[agentType]

    // 使用者可覆蓋
    if requested != "" {
        config.Runtime = string(requested)
    }

    return config
}

4.7 常見陷阱

陷阱 1：Session 狀態過大

// 錯誤：儲存所有對話歷史
session.History = append(session.History, turn)  // 無限增長

// 正確：定期摘要，只保留近期詳細記錄
if len(session.History) > 100 {
    summary := summarize(session.History[:50])
    session.History = append([]Turn{summary}, session.History[50:]...)
}

陷阱 2：Memory Bank 檢索過慢

// 錯誤：線性掃描所有記憶
for _, memory := range allMemories {
    if match(memory, query) {
        results = append(results, memory)
    }
}

// 正確：使用向量資料庫
memories := pgvector.Search(queryEmbedding, limit)

陷阱 3：Sandbox 資源洩漏

// 錯誤：建立後忘記銷毀
sandbox := controller.CreateSandbox(spec)
// ... 使用 ...
// 忘記銷毀！

// 正確：使用 defer 或 context
func runInSandbox(ctx context.Context, spec *SandboxSpec, fn func()) error {
    sandbox, err := controller.CreateSandbox(ctx, spec)
    if err != nil {
        return err
    }
    defer controller.DestroySandbox(ctx, sandbox)  // 確保銷毀

    fn()
    return nil
}

4.8 總結

SCALE 層的核心是讓 Agent 在生產環境可靠運行：

  1. Google AX：提供 Durable Execution、事件溯源、多 Agent 協作
  2. Agent Runtime：管理生命週期、健康檢查、自動恢復
  3. Session Manager：分層儲存策略（Hot/Warm/Cold）
  4. Memory Bank：跨 Session 長期記憶，支援檢索和壓縮
  5. Sandbox Controller：動態建立隔離環境

關鍵原則：
- 所有狀態都要持久化
- 故障是自動恢復，不是人工介入
- 資源使用要有上限和清理機制
