第 2 章：通訊架構

第 2 章：通訊架構 — Agent 的神經系統

2.1 問題：Agent 之間如何對話？

當你有多個 Agent 需要協作時，第一個要解決的問題是：它們如何溝通？

這個問題比看起來更複雜。讓我們考慮一個真實場景：

使用者: "幫我分析這個 GitHub 專案的程式碼品質"

Orchestrator: "收到，我來拆解這個任務"
  ├── 子任務 1: 下載原始碼 → 指派給 Coding Agent
  ├── 子任務 2: 執行靜態分析 → 指派給 Coding Agent
  ├── 子任務 3: 查詢漏洞資料庫 → 指派給 Browser Agent
  ├── 子任務 4: 生成報告 → 指派給 Data Agent
  └── 子任務 5: 審查結果 → 指派給 Review Agent

這裡的通訊需求包括：

  1. Orchestrator → Agent：下達任務指令
  2. Agent → Orchestrator：回報進度和結果
  3. Agent → Agent：直接協作（如 Coding Agent 請求 Browser Agent 查詢資料）
  4. Agent → Tool：呼叫外部工具
  5. 系統廣播：狀態變更通知所有相關方

傳統的 REST API 無法優雅地處理這些需求：

  • 同步呼叫會阻塞 Orchestrator
  • 輪詢進度浪費資源
  • 一對多通訊需要複雜的服務發現
  • 斷線後難以恢復狀態

我們需要一個事件驅動的訊息系統。

圖：NATS 作為中心樂紐，連接所有 Agent，支援多種通訊模式

2.2 為什麼選擇 NATS？

NATS 是一個輕量級、高效能的訊息系統。選擇它有幾個關鍵原因：

2.2.1 原生支援多種通訊模式

// 1. 發布-訂閱（廣播）
nc.Publish("agents.status", data)

// 2. 請求-回覆（RPC）
resp, err := nc.Request("agents.coding-agent.rpc", req, timeout)

// 3. 佇列（負載均衡）
sub, _ := nc.QueueSubscribe("tasks.new", "worker-group", handler)

// 4. JetStream（持久化）
js.Publish("tasks.important", data)

2.2.2 輕量級且高效能

NATS 伺服器僅需數 MB 記憶體，單機可處理數百萬條訊息/秒。這對於需要頻繁通訊的 Agent 系統至關重要。

2.2.3 雲原生友好

NATS 有成熟的 Kubernetes Operator，支援自動擴展、持久化儲存、TLS 加密。

2.3 雙軌通訊設計

我們採用雙軌通訊策略：

圖：軌道 1 控制平面負責輕量級調度，軌道 2 資料平面負責豐富的 Agent 對話

圖：雙軌通訊詳細設計：軌道 1 控制平面負責輕量級調度，軌道 2 資料平面負責豐富的 Agent 對話

2.3.1 為什麼需要雙軌？

NATS 原生適合：
- 系統級控制訊號（心跳、狀態、調度）
- 需要持久化的重要事件
- 一對多廣播

A2A Protocol 適合：
- Agent 之間的語意對話
- 需要結構化任務定義的互動
- 跨平台互操作（不同框架的 Agent）

分離這兩個軌道讓我們能夠獨立優化：NATS 軌道追求極致效能，A2A 軌道追求語意豐富度。

2.4 Subject 設計

Subject（主題）是 NATS 的核心概念。好的 Subject 設計能讓系統更易於理解和維護。

// 任務相關
tasks.new              // 新任務發布
tasks.assigned.{id}    // 任務已分配
tasks.progress.{id}    // 任務進度更新
tasks.completed.{id}   // 任務完成
tasks.failed.{id}      // 任務失敗

// Agent 相關
agents.{id}.heartbeat  // Agent 心跳
agents.{id}.status     // Agent 狀態變更
agents.{id}.rpc        // Agent RPC 端點
agents.{id}.events     // Agent 事件

// 系統相關
system.config.updated  // 配置更新
system.agent.registered // Agent 註冊
system.agent.deregistered // Agent 註銷

// 記憶相關
memory.{user_id}.read  // 讀取使用者記憶
memory.{user_id}.write // 寫入使用者記憶

// 審計相關
audit.{agent_id}.{tool} // Agent 工具呼叫審計

2.5 A2A Protocol 實作

A2A (Agent-to-Agent) Protocol 是 Google 提出的 Agent 互動標準。我們來看看核心資料模型：

// Task 是 A2A 的核心概念
type Task struct {
    ID          string      `json:"id"`
    SessionID   string      `json:"session_id"`
    Status      TaskStatus  `json:"status"`
    Message     *Message    `json:"message"`
    Artifacts   []Artifact  `json:"artifacts"`
    History     []Message   `json:"history"`
    CreatedAt   time.Time   `json:"created_at"`
    UpdatedAt   time.Time   `json:"updated_at"`
}

// Message 代表一次互動
type Message struct {
    Role    string   `json:"role"`    // "user" | "agent" | "system"
    Parts   []Part   `json:"parts"`
}

// Part 是訊息的內容單元
type Part struct {
    Type     string `json:"type"`     // "text" | "file" | "data"
    Content  string `json:"content"`
    Metadata map[string]interface{} `json:"metadata,omitempty"`
}

2.5.1 任務生命週期

Submitted → Working → Input-Required → Working → Completed
                ↓
            Failed / Canceled

關鍵設計：任務狀態是單向的。一旦完成或失敗，就不能回退。這簡化了狀態管理，避免了複雜的狀態機。

2.5.2 Agent Card

每個 Agent 都有一張「名片」，描述它的能力：

type AgentCard struct {
    Name        string            `json:"name"`
    Description string            `json:"description"`
    Version     string            `json:"version"`
    Capabilities []string         `json:"capabilities"`
    Skills      []SkillInfo       `json:"skills"`
    Endpoint    string            `json:"endpoint"`
    Authentication AuthInfo       `json:"authentication"`
}

Agent Card 儲存在 NATS KV 中，便於動態發現：

// 註冊 Agent Card
kv.Put("agents.cards.coding-agent", cardJSON)

// 發現 Agent
entry, _ := kv.Get("agents.cards.coding-agent")

2.6 程式碼範例：基礎通訊

讓我們看看實際的 Go 程式碼：

package main

import (
    "context"
    "fmt"
    "time"

    "github.com/nats-io/nats.go"
    "github.com/nats-io/nats.go/jetstream"
)

func main() {
    // 連線到 NATS
    nc, _ := nats.Connect(nats.DefaultURL)
    defer nc.Close()

    // 建立 JetStream 上下文
    js, _ := jetstream.New(nc)

    // 建立 Stream（持久化訊息）
    ctx := context.Background()
    stream, _ := js.CreateStream(ctx, jetstream.StreamConfig{
        Name:     "TASKS",
        Subjects: []string{"tasks.>"},
        Retention: jetstream.WorkQueuePolicy,
    })

    // 發布任務
    task := Task{
        ID:      "task-001",
        Status:  TaskStatusSubmitted,
        Message: &Message{
            Role: "user",
            Parts: []Part{{
                Type:    "text",
                Content: "分析這個專案的程式碼品質",
            }},
        },
    }

    taskJSON, _ := json.Marshal(task)
    js.Publish(ctx, "tasks.new", taskJSON)

    // 訂閱任務
    cons, _ := stream.CreateConsumer(ctx, jetstream.ConsumerConfig{
        Durable:   "coding-agent",
        FilterSubject: "tasks.new",
    })

    // 處理任務
    cons.Consume(func(msg jetstream.Msg) {
        var task Task
        json.Unmarshal(msg.Data(), &task)

        fmt.Printf("收到任務: %s\n", task.ID)

        // 處理完成後確認
        msg.Ack()
    })

    time.Sleep(time.Hour)
}

2.7 常見陷阱

陷阱 1：Subject 設計過於扁平

// 錯誤：所有訊息混在一起
nc.Subscribe("agent.*", handler)  // 難以過濾

// 正確：階層式設計
nc.Subscribe("agents.coding-agent.>", handler)  // 精確匹配

陷阱 2：忽略訊息順序

// 錯誤：多個 Consumer 並行處理，順序不保證

// 正確：使用單一 Consumer 或顯式排序
cons, _ := stream.CreateConsumer(ctx, jetstream.ConsumerConfig{
    Durable:   "ordered-consumer",
    DeliverPolicy: jetstream.DeliverAllPolicy,
})

陷阱 3：忘記處理斷線

// 錯誤：直接連線，無重連邏輯
nc, _ := nats.Connect(url)

// 正確：配置重連和緩衝
nc, _ := nats.Connect(url,
    nats.MaxReconnects(10),
    nats.ReconnectWait(time.Second),
    nats.ReconnectBufSize(5*1024*1024), // 5MB 緩衝
)

2.8 總結

通訊架構是 Agent 平台的神經系統。我們選擇 NATS 作為基礎，因為它：

  1. 支援多種通訊模式（Pub-Sub、Queue、RPC、持久化）
  2. 輕量級且高效能
  3. 雲原生友好

雙軌設計（NATS 原生 + A2A Protocol）讓我們能夠兼顧效能和語意豐富度。
