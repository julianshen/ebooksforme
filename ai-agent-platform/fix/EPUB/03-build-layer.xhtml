第 3 章：BUILD 層

第 3 章：BUILD 層 — 開發 Agent

3.1 問題：如何開發一個好的 Agent？

開發 Agent 和開發傳統軟體有本質區別。

傳統軟體的邏輯是確定的：給定輸入 A，永遠輸出 B。Agent 的邏輯是概率的：給定輸入 A，可能輸出 B、C 或 D，取決於模型、上下文和隨機性。

這帶來了幾個挑戰：

  1. 不可預測性：Agent 可能產生意料之外的輸出
  2. 狀態管理：Agent 需要記住對話歷史和上下文
  3. 工具整合：Agent 需要安全地呼叫外部工具
  4. 錯誤恢復：Agent 可能在工具呼叫失敗後陷入迴圈

我們需要一個框架來管理這些複雜性。

3.2 Google ADK 深度解析

Google Agent Development Kit（ADK）是 Google 開源的 Agent 開發框架，提供 Python、Go、Java、TypeScript、Kotlin 多語言支援。本章從設計哲學、原始碼結構到實作細節進行深度剖析。

3.2.1 ADK 設計哲學

從原始碼結構可以看出 ADK 的幾個核心設計原則：

  • Agent 即組合：LlmAgent、LoopAgent、ParallelAgent、SequentialAgent 都繼承 BaseAgent，支援任意組合
  • 事件驅動：所有 Agent 通過 AsyncGenerator[Event, None] 產生事件，Runner 統一調度
  • 會話隔離：SessionService 負責管理對話狀態，支援 InMemory、SQLite、Vertex AI 多種後端
  • 工具優先：FunctionTool 自動從 Python 函式生成 schema，支援同步/非同步、串流
  • 記憶分層：區分 Session State（短期）與 Memory Service（長期）

3.2.2 ADK 原始碼結構總覽

ADK Python 原始碼主要分為以下模組：

模組職責關鍵檔案

flows/LLM 呼叫流程auto_flow.py, single_flow.py, functions.py

3.2.3 LlmAgent 原始碼剖析

LlmAgent 是 ADK 最核心的 Agent 類型，原始碼長達 1138 行。其核心運作流程：

# 簡化後的 LlmAgent 執行流程
class LlmAgent(BaseAgent):
    async def _run_async_impl(self, ctx: InvocationContext):
        # 1. 載入歷史上下文
        history = self._load_history(ctx)
        
        # 2. 構建 LLM 請求
        llm_request = self._build_llm_request(ctx, history)
        
        # 3. 呼叫模型（支援 BeforeModel/AfterModel callback）
        response = await self._call_model(ctx, llm_request)
        
        # 4. 處理模型輸出
        async for event in self._process_response(ctx, response):
            yield event
            
            # 5. 如果包含 function call，執行工具
            if event.has_function_call():
                tool_result = await self._execute_tool(ctx, event)
                yield tool_result
                
                # 6. 遞迴繼續，直到沒有新的 function call
                async for follow_up in self._run_async_impl(ctx):
                    yield follow_up

關鍵設計細節：

  • BeforeModelCallback：在呼叫 LLM 前攔截請求，可用於添加系統提示、RAG 上下文
  • AfterModelCallback：在收到 LLM 回應後處理，可用於輸出過濾、格式轉換
  • OnModelErrorCallback：模型呼叫失敗時的降級策略
  • ToolContext：每個工具呼叫都帶有上下文，包含 auth、artifact service、memory service

3.2.4 Agent 組合模式

ADK 支援四種組合模式，原始碼中都有對應實現：

1. SequentialAgent（順序執行）

# 原始碼核心邏輯
async def _run_async_impl(self, ctx):
    for sub_agent in self.sub_agents:
        async for event in sub_agent.run_async(ctx):
            yield event
            if ctx.should_pause_invocation(event):
                return  # 暫停後續執行

特點：前一個 Agent 完成後才執行下一個，適合流水線處理。

2. ParallelAgent（並行執行）

# 原始碼核心邏輯
async with asyncio.TaskGroup() as tg:
    for events_for_one_agent in agent_runs:
        tg.create_task(process_an_agent(events_for_one_agent))

特點：使用 Python 3.11+ 的 TaskGroup，每個子 Agent 有獨立的 branch context（invocation_context.branch），事件通過 asyncio.Queue 合併。

3. LoopAgent（迴圈執行）

# 原始碼核心邏輯
while (not max_iterations or times_looped < max_iterations):
    for sub_agent in self.sub_agents:
        async for event in sub_agent.run_async(ctx):
            yield event
            if event.is_escalate():
                return  # 子 Agent 要求升級，退出迴圈

特點：持續迭代直到滿足終止條件，適合需要反覆精煉的任務。

4. LlmAgent 作為 Orchestrator

LlmAgent 通過 sub_agents 參數和 transfer_to_agent_tool 實現動態路由：

orchestrator = LlmAgent(
    name="task_orchestrator",
    model="gemini-2.0",

    sub_agents=[coding_agent, research_agent, review_agent],
    # ADK 自動將 sub_agents 註冊為可轉移工具
)

3.2.5 Runner：執行引擎核心

Runner 是 ADK 的心臟，負責協調 Agent、Session、Tools、Memory。原始碼長達 2264 行。

Runner 的核心職責：

  • 會話管理：創建/恢復 Session，處理事件追加
  • 事件路由：將用戶輸入、模型輸出、工具結果按正確順序組裝
  • 可恢復執行：通過 is_resumable 和 should_pause_invocation 支援中斷恢復
  • 任務隔離：通過 isolation_scope 區分不同任務 Agent 的上下文

關鍵程式碼片段：

# Runner._append_user_event 的任務隔離邏輯
def _find_active_task_isolation_scope(session):
    """從會話歷史中找出當前暫停的任務 Agent 的 scope。
    
    兩種任務委派方式：
    1. Function Call 委派：scope = fc.id，由未解決的任務 FC 開啟
    2. Workflow 節點：scope = @，由任務 Agent 產生的事件標記
    
    兩種方式都在 finish_task 成功回應時關閉 scope。
    """
    finished_scopes = set()
    for event in reversed(session.events):
        scope = event.isolation_scope
        if not scope:
            continue
        # 檢查是否已被後續的 finish_task 關閉
        if event.is_successful_finish_task():
            finished_scopes.add(scope)
            continue
        if scope not in finished_scopes:
            return scope
    return None

3.2.7 Tools：從函式到結構化工具

ADK 的 FunctionTool 會自動從 Python 函式生成模型可用的工具定義：

class FunctionTool(BaseTool):
    def __init__(self, func: Callable, require_confirmation=False):
        # 1. 提取函式名稱和文檔
        name = func.__name__
        doc = inspect.cleandoc(func.__doc__ or "")
        
        # 2. 檢測特殊參數
        self._context_param_name = find_context_parameter(func) or 'tool_context'
        self._ignore_params = [self._context_param_name, 'input_stream']
        
        # 3. 從 type hints 生成 FunctionDeclaration
        self._declaration = build_function_declaration(
            func=func,
            ignore_params=self._ignore_params,
        )

進階特性：

  • require_confirmation：支援布林值或回調函式，動態決定是否需要用戶確認
  • ToolContext：注入工具上下文，包含當前會話、授權憑證、artifact service
  • AuthenticatedFunctionTool：支援 OAuth2、Service Account 等認證流程
  • MCP Tool：通過 mcp_tool.py 整合 Model Context Protocol 服務

3.2.9 ADK 與 AX 的整合

Google AX 提供了一個 ADK Agent Server，將 ADK Agent 包裝為 AX 的遠程 Agent：

# python/adk/adk_agent_server.py 核心邏輯
class ADKAgentServicer(ax_pb2_grpc.AgentServiceServicer):
    def __init__(self, agent, debug=False):
        self.agent = agent
        self.session_service = InMemorySessionService()
        self.runner = Runner(
            session_service=self.session_service,
            agent=self.agent,
            app_name=self.agent.name
        )

    async def Connect(self, request_iterator, context):
        async for request in request_iterator:
            # 每次請求使用獨立的 UUID session，確保無狀態隔離
            session = await self.session_service.create_session(
                app_name=self.agent.name,
                user_id="AX_USER",
                session_id=str(uuid.uuid4())
            )
            
            # 歷史消息水合到 session（不執行）
            for msg in historical_messages:
                await self.session_service.append_event(session, event)
            
            # 只執行最後一條消息
            async for event in self.runner.run_async(
                session_id=session.id,
                user_id=session.user_id,
                new_message=content
            ):
                yield ax_message
            
            # 清理 session 釋放資源
            await self.session_service.delete_session(...)

整合要點：

  • AX 的 AgentService.Connect 是雙向 gRPC 串流
  • ADK 的 Event 通過 content_conversion.py 轉換為 AX 的 Content protobuf
  • 每次 AX 呼叫都創建新 session，執行完畢後刪除，確保隔離
  • 支援 text、thought、confirmation 三種內容類型轉換

Planner：將使用者請求拆解為 Task Graph

def plan_task(user_request: str) -> TaskGraph:
    """將使用者請求拆解為可執行的子任務圖"""
    # 使用 LLM 分析請求
    analysis = llm.analyze(user_request)

Router：根據任務特性選擇 Agent

def route_task(task: Task) -> Agent:
    """根據任務類型選擇最合適的 Agent"""
    routing_table = {
        TaskType.CODE_REVIEW: coding_agent,
        TaskType.WEB_SEARCH: browser_agent,
        TaskType.DATA_ANALYSIS: data_agent,
        TaskType.QUALITY_CHECK: review_agent,
    }

    return routing_table.get(task.type, default_agent)

Monitor：追蹤任務執行，處理逾時和重試

class TaskMonitor:
    def monitor(self, task: Task):
        """監控任務執行狀態"""
        start_time = time.time()

        while task.status != TaskStatus.COMPLETED:
            elapsed = time.time() - start_time

            # 逾時檢查
            if elapsed > task.timeout:
                self.handle_timeout(task)
                break

            # 進度檢查
            if task.status == TaskStatus.STUCK:
                self.handle_stuck(task)
                break

            time.sleep(1)

    def handle_timeout(self, task: Task):
        """處理逾時任務"""
        task.status = TaskStatus.TIMEOUT

        # 通知相關方
        self.notify_orchestrator(task)

        # 嘗試優雅終止
        self.graceful_shutdown(task)

3.4 Tool Registry（MCP Hub）

Agent 的能力來自於工具。我們需要一個中心化的工具管理系統。

3.4.1 為什麼需要 Tool Registry？

  1. 統一管理：所有工具集中註冊，便於發現和授權
  2. 權限控制：不同 Agent 可使用的工具不同
  3. 審計追蹤：記錄誰在什麼時候呼叫了什麼工具
  4. 版本管理：工具升級不影響 Agent

3.4.2 設計

type ToolRegistry struct {
    tools    map[string]*Tool      // 工具名稱 → 工具定義
    permits  map[string][]string   // Agent ID → 允許的工具列表
    auditLog jetstream.JetStream   // 審計日誌
}

type Tool struct {
    Name        string            `json:"name"`
    Description string            `json:"description"`
    InputSchema jsonschema.Schema `json:"input_schema"`
    Handler     ToolHandler       `json:"-"`
    RateLimit   *RateLimitConfig  `json:"rate_limit,omitempty"`
}

3.4.3 使用範例

// 註冊工具
registry.Register(&Tool{
    Name:        "file.read",
    Description: "讀取檔案內容",
    InputSchema: jsonschema.Schema{
        Type: "object",
        Properties: map[string]jsonschema.Schema{
            "path": {Type: "string"},
        },
        Required: []string{"path"},
    },
    Handler: func(ctx context.Context, input map[string]interface{}) (interface{}, error) {
        path := input["path"].(string)
        return os.ReadFile(path)
    },
})

// 授權 Agent 使用工具
registry.Permit("coding-agent", "file.read")
registry.Permit("coding-agent", "file.write")
registry.Deny("browser-agent", "file.write")  // Browser Agent 不能寫檔案

// 呼叫工具（帶審計）
result, err := registry.CallWithAudit(ctx, "coding-agent", "file.read", map[string]interface{}{
    "path": "/app/main.go",
})

3.5 RAG Engine

Agent 需要存取領域知識。RAG (Retrieval-Augmented Generation) 是標準方案。

3.5.1 架構

3.5.2 實作

from sentence_transformers import SentenceTransformer
import psycopg2

class RAGEngine:
    def __init__(self):
        self.encoder = SentenceTransformer('all-MiniLM-L6-v2')
        self.db = psycopg2.connect("postgresql://localhost/rag")

    def index_document(self, doc_id: str, content: str):
        """索引文件"""
        # 分塊
        chunks = self.chunk_text(content)

        # 生成向量
        embeddings = self.encoder.encode(chunks)

        # 儲存到資料庫
        with self.db.cursor() as cur:
            for chunk, embedding in zip(chunks, embeddings):
                cur.execute("""
                    INSERT INTO documents (doc_id, chunk, embedding)
                    VALUES (%s, %s, %s)
                """, (doc_id, chunk, embedding.tolist()))

        self.db.commit()

    def retrieve(self, query: str, top_k: int = 5) -> List[str]:
        """檢索相關內容"""
        # 生成查詢向量
        query_embedding = self.encoder.encode([query])[0]

        # 向量搜尋
        with self.db.cursor() as cur:
            cur.execute("""
                SELECT chunk, embedding <=> %s AS distance
                FROM documents
                ORDER BY distance
                LIMIT %s
            """, (query_embedding.tolist(), top_k))

            return [row[0] for row in cur.fetchall()]

3.6 常見陷阱

陷阱 1：Agent 過度自信

# 錯誤：Agent 沒有驗證就提交修改
agent.run("修改這個 bug")
# 結果：修改了錯誤的程式碼，引入了更多 bug

# 正確：要求 Agent 先分析，再修改，最後驗證
agent.run("""
1. 分析這個 bug 的根本原因
2. 提出修改方案
3. 應用修改
4. 執行測試驗證
5. 如果測試失敗，回退修改
""")

陷阱 2：工具權限過大

# 錯誤：所有 Agent 都能使用所有工具
registry.Permit("*", "*")

# 正確：最小權限原則
registry.Permit("coding-agent", "file.read")
registry.Permit("coding-agent", "file.write")
registry.Deny("coding-agent", "network.request")  # Coding Agent 不需要網路

陷阱 3：忽略上下文視窗限制

# 錯誤：傳入整個程式碼庫
context = read_entire_codebase()  # 100k tokens
agent.run(context)  # 超出視窗限制，丟失資訊

# 正確：分塊處理，只傳入相關部分
relevant_files = search_relevant_files(query)
for file in relevant_files:
    agent.run(f"分析這個檔案: {file}")

3.7 總結

BUILD 層的核心是讓開發者能夠：

  1. 快速開發：用 ADK 的階層式架構組織 Agent
  2. 安全整合：通過 MCP Hub 管理工具權限
  3. 知識增強：用 RAG Engine 提供領域知識

關鍵原則：
- Agent 應該專注於單一職責
- 工具權限應該最小化
- 所有操作應該可審計
