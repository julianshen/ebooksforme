第 8 章：Google Agent Runtime 深度解析

8.1 背景：Google 的 Agent 戰略

2026 年 5 月，Google 在 I/O 大會上發布了三個開源專案，構成了完整的 Agent 執行生態。這不是偶然，而是 Google 內部多年實踐的沉澱。

Google 內部運行著數以萬計的 Agent，處理從程式碼審查到資料分析的各種任務。這些 Agent 每天執行數百萬次，有些任務持續數小時甚至數天。在這個過程中，Google 遇到了我們正在面對的所有問題——而且更嚴重。

Agent Executor (AX)、Agent Substrate、Agent Sandbox 就是 Google 給出的答案。

8.2.2 核心能力詳解

Durable Execution

這是 AX 最核心的創新。傳統的 Agent 執行是脆弱的：

實作機制：

// Event Log 是核心
type EventLog struct {
    entries []Event
    writer  io.Writer  // 單一寫入者
}

type Event struct {
    Sequence  int64       `json:"seq"`
    Timestamp time.Time   `json:"ts"`
    Actor     string      `json:"actor"`
    Action    string      `json:"action"`
    Payload   interface{} `json:"payload"`
}

// 寫入事件（序列化）
func (el *EventLog) Append(e Event) error {
    e.Sequence = int64(len(el.entries))
    el.entries = append(el.entries, e)
    return el.persist(e)
}

// 從 Snapshot 恢復
func (el *EventLog) ResumeFrom(snapshot Snapshot) error {
    // 1. 載入 Snapshot 狀態
    state := snapshot.State

    // 2. 重放 Snapshot 之後的事件
    for _, event := range el.entries[snapshot.Sequence+1:] {
        state = apply(state, event)
    }

    return nil
}

Trajectory Branching

這是 AX 最獨特的能力。它讓 Agent 能夠「平行宇宙」：

原始軌跡
├──► Step 1: 讀取需求
├──► Step 2: 設計方案 A
├──► Step 3: 實作方案 A
│         └──► [結果不確定]
│
│    Checkpoint: 在 Step 2 之後
│
├──► Branch 1: 方案 A（繼續）
│    ├──► Step 4a: 優化方案 A
│    └──► [結果: 80 分]
│
├──► Branch 2: 方案 B（分叉）
│    ├──► Step 4b: 實作方案 B
│    └──► [結果: 90 分] ← 選擇這個
│
└──► Branch 3: 方案 C（分叉）
     ├──► Step 4c: 實作方案 C
     └──► [結果: 70 分]

應用場景：

  1. 策略比較：並行嘗試多種解決方案
  2. A/B 測試：比較不同模型的表現
  3. 回朔修復：發現錯誤後回到檢查點
  4. 參數搜尋：嘗試不同參數組合

8.3 Agent Substrate

8.3.1 核心創新：Actor 多路復用

Agent Substrate 解決了 Kubernetes 的一個根本問題：Pod 太重了。

一個 K8s Pod 需要：
- 排程到節點（~1s）
- 拉取映像（~5-30s）
- 初始化容器（~1-5s）
- 啟動應用（~1-10s）

總計：10-60 秒

但 Agent 任務可能只持續幾秒鐘。如果每個任務都建立一個 Pod，大部分時間都在等待啟動。

Agent Substrate 的解決方案：預熱 Worker + Actor 多路復用。

傳統 K8s: 1 Task = 1 Pod
┌─────────┐ ┌─────────┐ ┌─────────┐
│ Task 1  │ │ Task 2  │ │ Task 3  │
│  (Pod)  │ │  (Pod)  │ │  (Pod)  │
│  啟動:  │ │  啟動:  │ │  啟動:  │
│  30s    │ │  30s    │ │  30s    │
│  執行:  │ │  執行:  │ │  執行:  │
│  5s     │ │  5s     │ │  5s     │
│  銷毀:  │ │  銷毀:  │ │  銷毀:  │
│  5s     │ │  5s     │ │  5s     │
└─────────┘ └─────────┘ └─────────┘
總時間: 120s，資源利用率: 12.5%

8.4 Agent Sandbox

8.4.1 定位：安全執行環境

Agent Sandbox 是 GKE 的原生功能，提供：

  1. gVisor 隔離：核心層級保護
  2. 聲明式管理：CRD 定義 Sandbox
  3. 溫水游泳池：預熱 Pod 即時分配
  4. 快照/恢復：狀態持久化

8.4.2 核心概念

SandboxClaim + SandboxTemplate

# 使用者請求
apiVersion: agentsandbox.gke.io/v1
kind: SandboxClaim
metadata:
  name: coding-task-123
spec:
  templateRef: coding-template
  resources:
    cpu: "2"
    memory: "4Gi"

# 管理員定義範本
apiVersion: agentsandbox.gke.io/v1
kind: SandboxTemplate
metadata:
  name: coding-template
spec:
  image: agent-sandbox/coding:latest
  tools:
    - git
    - pip
    - npm
  storage:
    size: 10Gi
  isolation: gvisor
  networkPolicy: default-deny

運作流程

使用者建立 SandboxClaim
    │
    ▼
Controller 匹配 SandboxTemplate
    │
    ▼
從 Warm Pool 分配或新建 Sandbox
    │
    ▼
分配穩定端點（Sandbox Router）
    │
    ▼
Agent 在 Sandbox 中執行
    │
    ▼
執行完成後銷毀或回收

8.7 總結

Google 的 Agent Runtime 設計揭示了幾個關鍵洞察：

  1. AX 是基礎設施，不是框架：它解決的是「如何可靠地執行 Agent」，不是「如何開發 Agent」

  2. Durable Execution 是生產門檻：沒有 Snapshot/Resume，長時間 Agent 任務無法投入生產

  3. Agent Substrate 重新定義了 K8s 上的 Agent 運行：N:1 多路復用 + Warm Pool 是關鍵

  4. 全開源策略降低了採用門檻：AX、Agent Substrate、Agent Sandbox 全部開源

  5. 與我們的技術棧高度匹配：AX 是 Go 實作，與我們的 Go Agent Runtime 完美契合

最終建議：
- 短期：維持現有設計，監控 AX 專案發展
- 中期：參考 AX 設計加入 Snapshot/Resume
- 長期：直接整合 google/ax，獲得 Durable Execution 和 Branching 能力
