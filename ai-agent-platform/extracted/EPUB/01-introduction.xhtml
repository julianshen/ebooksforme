1.1 從單一 Agent 到多 Agent 協作

1.1.1 單一 Agent 的局限

圖：複数のエージェントが協力して仕事を完成する様子

2023 年，ChatGPT 讓世界第一次見識到大型語言模型的威力。你可以問它任何問題，它會給出一個看似合理的答案。但很快，人們發現了它的局限：

  • 它無法瀏覽即時網頁
  • 它無法執行程式碼
  • 它無法與其他系統互動
  • 它的記憶僅限於當前對話

Agent 的概念應運而生。給 LLM 加上工具（瀏覽器、程式碼執行、檔案系統），它就能完成更複雜的任務。但這還不夠。

當任務變得足夠複雜時——比如「幫我分析這個開源專案的程式碼品質，找出潛在的安全漏洞，並生成修復建議」——單一 Agent 力不從心。這需要：

  1. 一個 Agent 讀取和理解程式碼
  2. 一個 Agent 執行靜態分析工具
  3. 一個 Agent 查詢漏洞資料庫
  4. 一個 Agent 生成修復建議
  5. 一個 Agent 審查結果的準確性

這就是多 Agent 協作的價值。

图：單一智能體面對複雜任務焦頭汞額，多智能體團隊則能協作完成

1.2 Manus AI 的啟示

Manus AI 在 2025 年初引發了廣泛關注。它的核心創新不是技術突破，而是產品形態的突破：

使用者給出一個高階目標，系統自動拆解、規劃、執行、驗證。

這聽起來簡單，但實作極其複雜。背後需要：

  • 任務規劃：將模糊目標拆解為可執行的子任務
  • 動態調度：根據子任務特性選擇合適的 Agent
  • 安全隔離：每個 Agent 在獨立環境中執行
  • 狀態同步：多個 Agent 之間共享上下文和進度
  • 品質保證：確保最終結果符合預期

這正是本書要解決的問題。

圖：使用者提出目標，Manus AI 自動拆解為多個可執行子任務，分派給不同 Agent 完成

1.3 Google GEAP 的四層架構

Google 的 Gemini Enterprise Agent Platform (GEAP) 提供了一個企業級的參考框架。它將 Agent 基礎設施分為四個層級：

圖：Google Gemini Enterprise Agent Platform 四層架構，關注點分離設計

BUILD（建構層）：如何設計和開發 Agent，包括 ADK 框架選型、A2A 協定實作、MCP Tool Registry。

SCALE（擴展層）：如何讓 Agent 在生產環境可靠運行，包括 Agent Runtime、Session 管理、Memory Bank、Sandbox 隔離。

GOVERN（治理層）：如何確保 Agent 的安全與合規，包括 Identity、NetworkPolicy、Agent Gateway、審計追蹤。

OPTIMIZE（優化層）：如何持續提升 Agent 品質，包括 Evaluation Framework、可觀測性、Prompt 優化。
- GOVERN 層的人專注於安全與合規
- OPTIMIZE 層的人專注於持續提升品質

這本書將按照這個框架，逐層深入剖析。

圖：不同專長的角色負責不同層級，清晰的關注點分離

1.4 本書的設計哲學

在深入技術細節之前，讓我先闡述這本書的設計哲學。

1.4.1 問題優先於方案

Boris Cherny 在《Programming TypeScript》中展現了一種思維模式：先理解問題的本質，再給出解決方案。

太多技術書籍犯了相反的錯誤：它們急於展示「怎麼做」，卻忽略了「為什麼要這樣做」。結果讀者學會了複製貼上配置，卻無法應對真實世界的變化。

在這本書中，每一個設計決策都會有清晰的推理過程。

1.4.2 生產環境優先

學術論文和概念驗證（PoC）有一個共同的問題：它們忽略了生產環境的複雜性。

一個在筆記本電腦上跑得好好的 Agent，到了生產環境可能會：

  • 因為網路不穩定而無限重試
  • 因為記憶體洩漏而慢慢拖垮整個節點
  • 因為權限配置錯誤而洩漏敏感資料
  • 因為缺乏監控而默默產生錯誤結果

本書的所有設計都會考慮生產環境的真實約束。

1.4.3 漸進式複雜度

我們不會一開始就建構一個完美的系統。相反，我們會：

  1. 從最簡單可行的版本開始（MVP）
  2. 識別瓶頸和風險
  3. 有針對性地增加複雜度
  4. 每個階段都有明確的驗證標準

這種方法確保我們不會過度設計，也不會在關鍵環節偷工減料。
